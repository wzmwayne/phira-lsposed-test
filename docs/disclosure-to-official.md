## 标题

【安全】成绩上传的反作弊校验可被客户端侧伪造（std 无暇度下限检查不足）

## 严重性

- **不是** RCE/数据泄露/账户安全类问题；是**榜单与 rks 完整性**问题。
- 核心事实：**判定发生在客户端，上报内容完全由客户端产生**——服务端无法
  验证任何"人真的打出了这个成绩"。

## 一、事实链（全部来自开源代码，可自行验证）

1. `prpr/src/judge.rs`：`LIMIT_PERFECT = 0.08` → perfect 宽容窗口 ±80ms；
2. autoplay 是内置模组，判定路径（`auto_play_update`）在客户端；
3. 上传门控 `prpr/src/scene/game.rs:949-957` 全部是**客户端检查**
   （offline_mode / UNRATED / use_keyboard / speed），且 `#[cfg(closed)]`；
4. `config.mods`（含 AUTOPLAY 位）由客户端持有并随记录上报——**客户端可
   在不置 AUTOPLAY 位的情况下强制走 autoplay 判定**（这是任意二进制/内存
   修改都能做到的，与任何特定工具无关）。

## 二、统计论证（核心，纯数学可自证）

perfect 窗口 ±80ms。设打击偏移 ~ N(0, σ)，单 note 落窗概率 ≈ erf(0.08/σ√2)：

| σ | 单 note 落窗 | 1000-note 全 perfect 概率 |
|---|---|---|
| 15ms | ~99.999% | 必然 |
| 20ms | ~99.998% | 必然 |
| 25ms | ~99.78% | ~11% |
| 30ms | ~99.7% | ~5% |
| 40ms | ~95.4% | ~10⁻²⁰ |

**结论**：σ ≤ 20~25ms 的"全 perfect + 非零 std"是顶尖玩家的**正常画像**，
在聚合层面与真人**统计上不可区分**。因此：

- 现状"std≈0 拒收"只是**下限检查**，只拦截最简单的情况；
- std 完全由客户端计算并上报 → **任何客户端都可改报任意 std 值**，
  例如报 σ≈20ms + 全 perfect，即可通过该检查；
- 服务端若仅凭聚合值，**不存在**能区分"伪造 20ms"与"真人 20ms"的算法。

## 三、实测证据（本地测试环境，不含实现细节）

- 强制 autoplay（未置 AUTOPLAY 模组位）的成绩 → 以正常成绩形态上报、
  std≈0 → **被服务端拒收，查询无记录**；
- 正常手动游玩（含全 perfect AP）→ **被接受，可查询**。

→ 证实两点：(a) 服务端现行防线就是 std 下限 + 客户端诚实性；
(b) 上传载荷仅含**聚合统计**（无逐 note 时序），服务端即便想做更深校验
也没有数据基础。

## 四、影响

- 任何掌握"客户端可被修改"这一前提的第三方，都可批量制造统计上
  与顶尖玩家不可区分的成绩，污染榜单与 rks；
- 若未来榜单关联活动奖励，影响将进一步放大；
- 音游圈子对此类问题的通行态度是"自动打歌成绩应被拒收"——现状防线
  只拦住了最懒的攻击。

## 五、建议的缓解（全部自动化、服务端侧、零人工）

理解团队人力有限，以下均为低成本自动方案，基于现有数据即可：

1. **行为侧校验（推荐，成本最低）**：服务端基于账号历史自动检查——
   新账号突然全 AP 高难谱、跨记录 std 高度一致（真人会波动）、同账号
   上传频率异常。这些都是现有 DB 上一条查询的事，零人工；
2. **载荷补充逐 note 时序（小客户端改动）**：使服务端可查偏移分布形状
   与谱面难度相关性，极大抬高伪造成本；
3. **顶分自动打标**：全 perfect + 低 std 的记录自动打标（SQL 级），仅对
   打标记录做极少量抽查，而非全面人工审核；
4. 承认**完美反作弊不可实现**（判定在客户端的必然结果），目标是让作弊
   "成本 > 收益"（威慑 + 离群检测），而非绝对拦截。
