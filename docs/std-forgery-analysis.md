# std（无暇度）伪造可行性分析（2026-08-23，本地闭源服务端实测补充）

> 本文档是**威胁建模/攻击面评估**材料，仅存于私有仓库，仅用于本地测试场景的
> 强度判断。**不得用于官方服务器**（合规边界）。只描述概念方向，不含可执行代码
> 与字节级配方。

## 1. 新证据：上传载荷极短（用户抓包）

用户对本地闭源服务端做上传测试时抓包发现：**上传请求体极短，估计只含聚合字段
（以 std 无暇度为主），不含逐 note 时序数据**。

### 含义（重要，修正此前评估）

- 服务端**无法做逐 note 校验**（数据里根本没有）；
- 服务端可做的校验收窄为：**聚合值合理性**（std 是否 ≈0 / 是否在人类区间、
  accuracy↔std 是否统计自洽）+ **行为侧**（局时、上传频率、账号曲线）+
  **顶分人工复核**；
- 我此前"伪造需先逆向闭源 encode_record 完整记录格式"的前置条件**大幅弱化**：
  若载荷只有几个聚合字段，字段定位与改写都容易得多。

## 2. "低级伪造"的可能实现方向（概念级）

### 方向 A：让游戏自己算出非零 std（"假装手抖"）

- **位置**：judge 的 auto 判定路径（现有 PATCH_AT 分支的同一区域）；
- **思路**：auto 体目前"时间到就写固定判定值 2、不产生时序"。若在写判定的同时
  往 note 的时序字段写入一个**小抖动**（伪随机 ±数 ms~数十 ms），游戏自身的
  std 累积就会自然非零；
- **特点**：std 是"游戏自己算出来的"，下游字段（accuracy/判定计数）天然自洽，
  不需要理解上传格式；
- **约束**：抖动要落在人类合理区间且与判定分布一致——全 perfect 配一个过大的
  std 反而是矛盾信号（完美窗口 ±0.08s，人类以 ~15ms 散布几乎不可能全进窗口）。

### 方向 B：改写上传载荷中的 std 字段

- **位置**：上传路径 / 记录序列化处；
- **前置**：从抓包与内存比对中确定 std 字段在载荷中的偏移（载荷短 → 偏移定位容易）；
- **特点**：直接改聚合值，最省事；但若服务端有 accuracy↔std 一致性校验，
  需同时伪造相关联字段，否则同样矛盾。

## 3. 伪造会留下的破绽（检测面）

| 破绽 | 说明 |
|---|---|
| 统计自洽 | 100% accuracy 配高 std / 高难度谱面配超低 std，都是矛盾信号 |
| 行为侧 | 一局时长 vs 谱面长度、同账号上传频率、历史成绩曲线 |
| 人工复核 | 超低 std 顶分打标 + 人工复核是音游界通行做法，聚合校验挡不住人眼 |

## 4. 结论

- 载荷极短 → "低级伪造"门槛**比我此前评估更低**（无需逆向完整记录格式）；
- 但服务端仍可叠加 accuracy↔std 一致性、行为侧校验与顶分人工复核，低级伪造
  在这些面前仍然可查；
- 对现有模块（std≈0 原样上报）：服务端 std 检查**有效**；
- 对恶意改造：std 检查是"威慑层"——挡得住懒人，挡不住决心足够大的攻击者，
  真正防线是**模块私有** + 服务端交叉校验 + 人工复核。

## 5. 与官方服务器披露的关系

若未来向官方做善意披露，本条是核心信息：**"上传载荷仅含聚合 std，客户端侧
可伪造" → 建议服务端增加 accuracy↔std 一致性校验与顶分人工复核**，无需公开
任何伪造实现细节。
