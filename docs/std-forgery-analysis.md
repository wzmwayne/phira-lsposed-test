# std（无暇度）伪造可行性分析（2026-08-23 本地实测 + 2026-08-23 统计更正）

> 本文档是**威胁建模/攻击面评估**材料，仅存于私有仓库，仅用于本地测试场景的
> 强度判断。**不得用于官方服务器**（合规边界）。只描述概念方向，不含可执行代码
> 与字节级配方。

## 1. 新证据：上传载荷极短（用户抓包）

用户对本地闭源服务端做上传测试时抓包发现：**上传请求体极短，估计只含聚合字段
（以 std 无暇度为主），不含逐 note 时序数据**。

### 含义（重要，修正此前评估）

- 服务端**无法做逐 note 校验**（数据里根本没有）；
- 服务端可做的校验收窄为：**聚合值合理性**（std 下限检查）+ **行为侧**（局时、
  上传频率、账号曲线）+ **顶分人工复核**；
- 我此前"伪造需先逆向闭源 encode_record 完整记录格式"的前置条件**大幅弱化**：
  若载荷只有几个聚合字段，字段定位与改写都容易得多。

## 1.5 ★ 统计更正（用户指出，正确）：全 perfect 配中等 std 不矛盾

perfect 宽容窗口 = ±0.08s（80ms）。若打击偏移 ~ N(0, σ)，单 note 落入窗口
概率 ≈ erf(0.08 / σ√2)，1000-note 谱面 AP 概率 ≈ P^n：

| σ | 单 note 在窗口内 | 1000-note AP 概率 |
|---|---|---|
| 10ms | ~100% | 必然 |
| 15ms | ~99.999% | 必然 |
| 20ms | ~99.998% | 必然 |
| 25ms | ~99.78% | ~11%（偶发） |
| 30ms | ~99.7% | ~5%（罕见） |
| 40ms | ~95.4% | ~10⁻²⁰（不可能） |

**结论**：σ ≤ 20~25ms 时"全 perfect + 非零 std"是顶尖玩家的**正常画像**，聚合
层面无破绽。真正的矛盾只在两端：
- **std ≈ 0**（非人，任何人类都有 ≥ 数 ms 抖动）→ 现状模块的指纹；
- **std ≳ 40ms 却 AP**（统计上不可能）。

→ 现实可行的伪造参数就是 **std ≈ 15~25ms + 全 perfect**：与真实顶尖玩家
**统计上不可区分**。服务端 std 检查（下限型）只能拦 std≈0 的"懒人攻击"。

## 2. "低级伪造"的可能实现方向（概念级）

### 方向 A：让游戏自己算出非零 std（"假装手抖"）

- **位置**：judge 的 auto 判定路径（现有 PATCH_AT 分支的同一区域）；
- **思路**：auto 体目前"时间到就写固定判定值 2、不产生时序"。若在写判定的同时
  往 note 的时序字段写入一个**伪随机小抖动**（σ≈15~25ms，正态或近似分布），
  游戏自身的 std 累积就落在人类合理区间；
- **特点**：std 是"游戏自己算出来的"，下游字段（accuracy/判定计数）天然自洽，
  不需要理解上传格式；
- **约束**：σ 选在 15~25ms 即可——全 perfect 与之完全兼容（见 §1.5），
  **不需要刻意压低**；唯一要避免的是 σ≈0 或 σ≳40ms 两端。

### 方向 B：改写上传载荷中的 std 字段

- **位置**：上传路径 / 记录序列化处；
- **前置**：从抓包与内存比对中确定 std 字段在载荷中的偏移（载荷短 → 偏移定位容易）；
- **特点**：直接改聚合值，最省事；目标值同样取 15~25ms；若载荷只有 std 一个
  敏感字段，则无"联动字段"需伪造。

## 3. 伪造会留下的破绽（检测面）

| 破绽 | 说明 |
|---|---|
| 统计自洽 | **只在两端可查**：std≈0 或 std≳40ms 配 AP；15~25ms 配 AP 与真人不可区分 |
| 行为侧 | **最强的剩余信号**：新账号突然 AP 高难谱、跨记录 std 高度一致（真人会有波动）、上传频率/局时异常 |
| 人工复核 | 超低 std / 全 AP 顶分打标 + 人工复核（音游界通行做法），聚合校验挡不住人眼 |

## 4. 结论

- 载荷极短 + 统计更正 → "低级伪造"门槛**远比我最初评估低**：伪造
  std≈15~25ms + 全 perfect 在聚合层面**无法被服务端区分**；
- 服务端现存 std 检查只拦 std≈0（现状模块），**拦不住参数合理的伪造**；
- 剩余有效防线：**行为侧校验（账号历史/跨记录一致性）+ 顶分人工复核**；
- 对现有模块（std≈0 原样上报）：服务端 std 检查**有效**；
- 对恶意改造：std 检查只是"威慑层"，真正防线是**模块私有** + 行为侧 + 人工复核。

## 5. 与官方服务器披露的关系

若未来向官方做善意披露，核心信息：**"上传载荷仅含聚合 std，客户端侧可伪造；
std 下限检查拦不住 σ≈15~25ms + 全 perfect 的伪造（与真人统计不可区分）" →
建议服务端增加行为侧校验（账号历史/跨记录一致性）与顶分人工复核**，无需公开
任何伪造实现细节。
